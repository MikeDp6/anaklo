## 0. Decisions (defaults binding for the builders; approved by Michalis on 2026-10-03 — see also §9)

**Database**
1. **The security effects of a membership change live in one trigger** (`business_members_access_changed`, §2.5), not in explicit calls of `set_member_role`/`remove_member`: on every DELETE of a membership row and every UPDATE that changes `role`, `user_id` or `business_id` (same condition as the 0007 push trigger), in the same transaction: all sessions of the user are revoked (`private.revoke_user_sessions_impl`, which also drops the user's push rows) and, when the user is owner/manager **nowhere** afterwards, all their factors are deleted with a `demotion` grant each. The RPCs inherit it (plan: «το `_impl` … στην ίδια συναλλαγή»), and so does provisioning (a hand-over or demotion by script can no longer leave a staff member with factors or live sessions). The 0007 push trigger stays as it is (dropping twice is harmless).
2. ⚠ **Owner/manager memberships need `aal2` on the server once the user has a verified factor** (beyond the plan text; it makes «για τον manager το TOTP προστατεύει τον λογαριασμό» true at the API). The membership helpers of 0001 (`my_business_ids`, `my_business_ids_with_role`, `my_staff_ids`, `is_member`, `has_role`, `my_staff_id`) count an owner/manager row only when `private.session_mfa_ok()`: the JWT is `aal2`, **or** the user has no verified factor (first sign-in, after an `mfa-reset`). Staff rows always count. Without it, a stolen email code (an `aal1` session) of an enrolled owner reads every client and amount straight from PostgREST; the UI challenge alone would not stop it. Consequences: an enrolled owner at `aal1` gets empty reads and `42501` **without hint** from every RPC (→ `decideAuthRoute` → challenge, exactly the plan's rule for 42501 without hint); `business_members_select` also shows the caller's **own** rows, so the loader still reads the role. pgTAP fixtures have no factor rows, so existing tests are unaffected. Cost ≈ 0.25 day. If refused: skip §2.4 except the policy change, and drop the D2 checks of §7.1-F.
3. **New domain errors** (`P0001`, same mechanism as 0004–0006): AN024 `slug_unavailable`, AN025 `future_appointments`, AN026 `last_owner`, AN027 `last_factor`, AN028 `already_member`, AN029 `staff_has_login`, AN030 `not_a_member` (§2.9).
4. **Invitations add `manager` or `staff` only** (plan «Μέλη και ταυτότητα» step 3). A new owner is added by promoting a member with `set_member_role` (same owner + fresh-code check). ADR-0009 §21 mentions «ρόλος owner στην πρόσκληση»; the plan text wins here.
5. **`list_members` RPC (owner only)** — not named in the plan, but the screen needs the members' emails, which live in `auth.users` (unreadable by `authenticated`). No freshness: reading is not critical.
6. **Who sees which screen:** «Μέλη» and «Ταυτότητα» owner only (critical actions, SPEC §5); «Ασφάλεια» every role (staff see only «Αποσύνδεση από όλες τις συσκευές»; owner/manager also their devices).
7. **Aliases:** `public_booking_catalogue(<alias>)` returns the **current** business's catalogue (no new shape: `business.slug` is the current slug); the Worker and the Vite middleware answer **301** to `/<current slug><query>` with `Cache-Control: no-store` (a browser must never cache a redirect that a later slug change could turn into a loop); the booking page, when it loaded the catalogue itself, only `history.replaceState`s the URL. A business may take back **its own** former slug (that alias row goes, the slug it leaves becomes an alias); a slug or alias never passes to another business (DB guard trigger). Aliases are kept forever in Phase 1.
8. **Time zone / currency are refused while an appointment `booked|confirmed` has `ends_at > now()`** (one in progress counts). The `replan_reminders_impl` call after a zone change (1.6 §7) is made anyway; while this refusal holds it has nothing to re-plan.
9. **Idempotency:** `set_member_role` with the current role → `changed: false`, nothing written (no audit, no revocation); `remove_member` of a user who is not a member → `removed: false`, nothing written; `add_member` with the same role and staff link → `added: false`; `change_business_identity` with nothing different → `changed: false`.
10. **Acting on oneself:** the RPCs allow it (an owner may step down or leave while another owner exists; the last owner never — AN026). The UI offers no action on the caller's own row in 1.7.
11. **`authorize_factor_change('remove')` refuses the last factor before asking for freshness** (no code sheet for a removal that would be refused anyway), and counts a factor with an unexpired, unmatched `remove` grant as already gone (two parallel removals of a user's two factors cannot both pass).
12. **Edge Function errors have the PostgREST shape** `{ code, message, hint }` (flat, `hint` null when absent), so one classifier serves RPCs and functions. RPC errors pass through unchanged: `42501` → 403 (with or without hint), `P0001` → the status of `DOMAIN_ERROR_HTTP_STATUS` (AN027 → **403**: the plan's «403 χωρίς hint» for the last factor; «χωρίς hint» = without one of the two step-up hints), `22023`/`22P02` → 400, else 500.
13. **`scripts/mfa-reset.mjs` is a dry run unless `--yes`**; the email templates live in the runbook (between markers) and the script prints them filled in.
14. **Provisioning of an existing business with changes requires `--reason` and `--ticket`** on dev/prod; with `--local` they default to `local provisioning` / `LOCAL`; `e2e/lib/shops.ts#provisionLocal` passes `e2e fixture` / `E2E`.
15. **The pending enrolment never stores the secret**: `sessionStorage` keeps `factorId`, name, mode and stage only; a resume at the QR stage starts the enrolment over (the QR cannot be shown again).
16. **Seed:** no factor is seeded for `owner@`/`manager@demo-barber.test`: a local manual sign-in as them enrols the developer's own authenticator (again after every `db:reset`). Seven new synthetic e2e users (§2.11).
17. **E2E sessions of owners are made through the API** (generateLink + verifyOtp + TOTP verify on the local stack, cached per user while ≥ 15′ valid), in setup projects for the demo shop and on demand for the provisioned shops. The UI enrolment/challenge flows are covered by their own specs on both engines.
18. ⚠ **SPEC §11 says the critical buttons «μπορούν να το ανοίξουν από πριν»**; the plan, ADR-0009 §12–13 and rule 13 say never proactively. Default: never (the freshness rule exists only in SQL); the SPEC sentence is removed at integration.
19. **Nous contact for «Χάσατε τη συσκευή σας;»:** `VITE_SUPPORT_EMAIL`, `VITE_SUPPORT_PHONE` (E.164); synthetic placeholders in `.env.example` until Michalis gives the real ones (prerequisite «Πριν το 1.7»; needed for real only at 1.10).
20. **Device names:** a free text field, default «Συσκευή {{n}}» (n = verified count + 1); the authenticator app shows the issuer `Anaklo` (`common:app.name`).
21. **The member-route loader calls `getUser()` on every run** (live factors, and a revoked session is noticed: GoTrue answers 401/403 `session_not_found` → local clean-up → login), in parallel with the membership read.
22. **Estimate:** D2, `list_members`, the alias guard and the API e2e sessions add ≈ 0.5 day to the 5 days of 1.7 (from the buffer).

### 2.3 Freshness (private, stable, **no grants**; only definer `_impl`s call them)

```
private.has_fresh_totp() returns boolean
  claims := auth.jwt()
  false unless claims->>'aal' = 'aal2'
  window := (select fresh_totp_max_age_seconds from private.platform_settings where id); null or <= 0 → false
  false unless jsonb_typeof(claims->'amr') = 'array'
  ts := max((e->>'timestamp')::numeric) over e in jsonb_array_elements(claims->'amr')
        where jsonb_typeof(e) = 'object' and e->>'method' = 'totp' and jsonb_typeof(e->'timestamp') = 'number'
  return ts is not null and ts >= extract(epoch from now()) - window          -- transaction clock; no upper bound

private.require_fresh_totp() returns void
  coalesce(auth.jwt()->>'aal', '') <> 'aal2' → raise 42501, message 'a code from the authenticator app is required', hint 'aal2_required'
  not private.has_fresh_totp()               → raise 42501, same message,                                   hint 'fresh_totp_required'
```
An `amr` entry is `{ "method": "<otp|totp|…>", "timestamp": <epoch seconds> }`; entries that are not objects, have another method, or a non-numeric timestamp are ignored (missing → `fresh_totp_required`). Window 0 → never fresh (the platform brake). These two functions are the **only** place of the rule (rule 13).

### 2.4 Membership helpers (D2)

- `private.session_mfa_ok() returns boolean` (stable, definer, **no grants**): `coalesce(auth.jwt()->>'aal','') = 'aal2' or not exists (select 1 from auth.mfa_factors f where f.user_id = (select auth.uid()) and f.status = 'verified')`.
- `create or replace` (same signatures, grants kept) of `private.my_business_ids()`, `my_business_ids_with_role(text[])`, `my_staff_ids()`, `is_member(uuid)`, `has_role(uuid, text[])`, `my_staff_id(uuid)`: each adds `and (m.role = 'staff' or private.session_mfa_ok())` to its `business_members` filter. Nothing else changes.
- `drop policy business_members_select …; create policy business_members_select on public.business_members for select to authenticated using (user_id = (select auth.uid()) or business_id in (select private.my_business_ids()));` — the caller always reads their own rows (the loader needs the role at `aal1`).

### 2.6 RPCs for `authenticated` (wrapper + `_impl` granted)

| Wrapper (parameters in this order) | Returns | Vol. | Role | Fresh code |
|---|---|---|---|---|
| `can_manage_members(p_business_id uuid)` | boolean (`true` or raises) | stable | owner | yes |
| `set_member_role(p_business_id uuid, p_user_id uuid, p_role text)` | jsonb | volatile | owner | yes |
| `remove_member(p_business_id uuid, p_user_id uuid)` | jsonb | volatile | owner | yes |
| `list_members(p_business_id uuid)` | table | stable | owner | no |
| `change_business_identity(p_business_id uuid, p_slug text default null, p_timezone text default null, p_currency text default null)` | jsonb | volatile | owner | yes |
| `authorize_factor_change(p_action text, p_factor_id uuid default null)` | jsonb | volatile | owner/manager anywhere | see below |

**`can_manage_members`**: membership; owner; `require_fresh_totp()`; returns `true`. The check of `invite-member` (§3.1).

**`set_member_role`**:
1. Membership; owner; fresh code. `p_user_id` null → `42501`; `p_role` not in `('owner','manager','staff')` → `22023`.
2. `pg_advisory_xact_lock(hashtextextended('members:' || p_business_id, 0))` (serialises the last-owner check: without it two owners demoting each other concurrently both see the other still owner, and the deferred `ensure_business_has_owner` passes in both transactions).
3. The target's row `for update`; none → **AN030**. Same role → return `{ user_id, role, previous_role: role, changed: false }`, nothing written.
4. Old role `owner`, new role not `owner`, no other owner → **AN026**.
5. `update public.business_members set role = p_role` (the trigger revokes the sessions, drops the push rows and, if the user is owner/manager nowhere now, deletes the factors with `demotion` grants); one audit row `member_role_changed`.
6. Returns `{ user_id, role, previous_role, changed: true }`. Promotion to owner/manager: the next sign-in of the user enrols (decideAuthRoute).

**`remove_member`**: steps 1–2 as above (no role argument); the row `for update`; none → `{ user_id, removed: false }`; the last owner → **AN026**; `delete` (trigger as above); audit `member_removed`; returns `{ user_id, removed: true, previous_role }`. The staff row of the calendar stays.

**`list_members`**: membership; owner. Rows (exactly): `user_id uuid, email text, role text, staff_id uuid, staff_name text, created_at timestamptz, last_sign_in_at timestamptz, is_self boolean`; order `owner, manager, staff`, then `email`, `user_id`. Emails from `auth.users` (definer).

**`change_business_identity`**:
1. Membership; owner; fresh code.
2. Normalise: `slug := lower(btrim(p_slug))`, `tz := btrim(p_timezone)`, `cur := upper(btrim(p_currency))` (null stays null = unchanged). Shape (`22023`): slug matches the `businesses_slug_format` regex; `private.is_valid_timezone(tz)`; `cur ~ '^[A-Z]{3}$'`.
3. The business row `for update`. Changed fields = the non-null values that differ. None → `{ business_id, slug, timezone, currency, changed: false, changed_fields: [], replanned: 0 }`, nothing written.
4. Slug changed: `private.is_reserved_slug(slug)`, the current slug of another business, or an alias of another business → **AN024**.
5. Time zone or currency changed and an appointment of the business with `status in ('booked','confirmed') and ends_at > now()` exists → **AN025** (D8).
6. Slug changed: delete the alias row `(slug, this business)` if any; insert the current (old) slug as an alias of this business; then `update businesses set slug/timezone/currency` (definer; `authenticated` keeps no column grant on them). A `23505` from a concurrent claim of the same slug → **AN024**.
7. Time zone changed: `replanned := private.replan_reminders_impl(p_business_id, now())` (1.6 §7).
8. One audit row `business_identity_changed`. Returns `{ business_id, slug, timezone, currency, changed: true, changed_fields: text[] (subset of 'slug','timezone','currency' in this order), replanned }`. `vertical` is never touched (D6 of the plan).

**`authorize_factor_change`** (no `p_business_id`: the plan's only exception; not in the 02 loop):
1. `auth.uid()` null → `42501`. The user is owner/manager in **no** business (`is_privileged_anywhere`, direct read) → `42501` **without hint** (staff never write factors, ADR-0009 §18).
2. Shape (`22023`): `p_action` not in `('add','remove')`; `remove` with null `p_factor_id`; `add` with a non-null `p_factor_id`.
3. `pg_advisory_xact_lock(hashtextextended('factors:' || uid, 0))`.
4. `remove`: the factor must be the user's own **verified** factor, else `42501` without hint. Remaining = verified factors of the user minus those with an unexpired, unmatched `remove` grant (D11); remaining ≤ 1 → **AN027**.
5. Freshness: `remove` → `require_fresh_totp()`; `add` → `require_fresh_totp()` only when the user has a verified factor (the first enrolment, also after an `mfa-reset`, needs none and passes at `aal1`).
6. `write_factor_grant(uid, p_action, p_factor_id, 'user')`; one audit row per business where the user is owner/manager (`factor_add_authorized` / `factor_remove_authorized`).
7. Returns `{ grant_id, user_id, action, factor_id, expires_at }`.

```ts
enrollTotp(friendlyName: string, issuer: string): Promise<{ factorId: string; qrDataUri: string; secret: string; uri: string }>
                                              // mfa.enroll({ factorType: 'totp', friendlyName, issuer }); issuer = t('common:app.name')
verifyTotp(factorId: string, code: string): Promise<VerifyOutcome>   // challengeAndVerify; one new challenge on expiry
stepUpVerify(factorId: string, code: string): Promise<VerifyOutcome> // verifyTotp, then auth.refreshSession()
removeFactor(factorId: string): Promise<void>  // functions.invoke('manage-factors', { body: { action: 'remove', factor_id } })
type VerifyOutcome = { ok: true } | { ok: false; reason: 'invalid_code' | 'rate_limited' | 'offline' | 'unknown' }
```
`mfa.unenroll` is never called for a verified factor (also not by any other module; a Vitest searches `src/` for `mfa.unenroll` outside `mfaApi.ts`). The QR is used only when it starts with `data:image/svg+xml`, as `<img src alt>`; otherwise the screen shows the key only. Never `dangerouslySetInnerHTML`.

### 6.4 Enrolment wizard (`EnrollWizard` + one component per step; modes `first` | `second` | `add`)

- Step 1 «Κατέβασε μια εφαρμογή κωδικών» + the device name field (D20) + «Την έχω».
- Entering step 2 (generation): (a) `unenrollUnverified` for every unverified factor; (b) `stepUp(() => authorizeFactorAdd())` (`first`: passes at `aal1`; `second`/`add`: may open the sheet); (c) `enrollTotp(name)`; save the pending enrolment `{ userId, factorId, friendlyName, mode, stage: 'scan', createdAt }` in `sessionStorage` key `anaklo.pro.pendingEnrollment` (`src/features/auth/pendingEnrollment.ts`, expiry 30′, other user → ignored). Step 2 shows the QR `<img>`, «Άνοιγμα στην εφαρμογή κωδικών» (`<a href={uri}>`), the key with «Αντιγραφή κλειδιού», «Επόμενο»; any of the three sets `stage: 'code'`. A name conflict (GoTrue `mfa_factor_name_conflict`) → back to step 1 with the error.
- Step 3 «Γράψε τον κωδικό 6 ψηφίων»: `verifyTotp` → ok: clear the pending enrolment, invalidate `mfaFactors`; `first` → `/mfa/second-device` (replace); `second` → `next` or `/`; `add` → `/settings/security` with «Η συσκευή προστέθηκε.».
- Resume on mount: pending `stage 'code'` → step 3 with that factor and «Ξεκίνα από την αρχή» (unenrolls it); pending `stage 'scan'` → unenroll it and generate again (D15). The secret, QR and URI live only in component state.
- `MfaEnrollPage` (blocking, mode `first`): no way into the app until verified; only «Αποσύνδεση».

### 6.6 Step-up (shared layer, UI-AUTH writes it first)

`rpcError.ts` — `RpcFailureInfo` gains, classified before `forbidden`:
```ts
| { readonly kind: 'stepUp'; readonly hint: StepUpHint }   // code '42501' and hint ∈ STEP_UP_HINTS
| { readonly kind: 'stepUpCancelled' }                      // thrown by withStepUp when the sheet is closed
| { readonly kind: 'unauthorized' }                         // HTTP 401, or PGRST301/PGRST303
```
`rpcFailureMessageKey`: `stepUp` → `pro:stepUp.failed`, `stepUpCancelled` → `pro:stepUp.cancelled`, `unauthorized` → `pro:errors.forbidden`. Every exhaustive switch over the kinds is updated; `useSettingsMutation` invalidates after `forbidden`/`unauthorized` as after `forbidden` today and never locks on the new kinds.

`functionError.ts`: `throwIfFunctionFailed(error: unknown): Promise<void>` — `FunctionsHttpError` → `status` and `FunctionErrorBody` from `error.context` → `RpcFailure(classifyRpcFailure(body, status))` (so a 403 `{ code: '42501', hint }` is `stepUp`); `FunctionsFetchError` → `offline`; anything else → `unknown`.

`step-up.ts` (pure):
```ts
export interface StepUpDeps { askForCode(hint: StepUpHint): Promise<boolean>; onAuthRecheck(): void }
export class StepUpCancelled extends RpcFailure {}            // failure { kind: 'stepUpCancelled' }
export async function withStepUp<T>(call: () => Promise<T>, deps: StepUpDeps): Promise<T>
```
1. `call()` succeeds → its result; `askForCode` is never called (no proactive opening, D18).
2. Failure `stepUp` → `askForCode(hint)` → `false` → throw `StepUpCancelled`; `true` → `call()` **once more**; that second call's result or error is final (another `stepUp` → thrown as is, no second sheet, no third call).
3. Failure `forbidden` or `unauthorized` (on the first or the retried call) → `onAuthRecheck()`, rethrow.
4. Anything else → rethrow.

`hooks/useStepUp.ts`: `useStepUp(): <T>(call: () => Promise<T>) => Promise<T>` bound to the `StepUpProvider` (in `ProShell`, around every route) and to `router.revalidate`. `askForCode` opens `StepUpSheet` (the 1.4 `Sheet`); concurrent requests share one open sheet. The sheet: title, the plan's sentence, device radio when ≥ 2 verified factors, the code field, «Συνέχεια» → `stepUpVerify` → ok → closes, resolves `true`; wrong code → inline error, stays open (attempts in the sheet are verifications, not retries of the action); «Άκυρο»/close → `false`; no verified factor → `false` and `onAuthRecheck()`.

**Review fixes (after integration, 2026-10-02; local only)**

Eight confirmed review findings (two of them the same defect). Each fix has a test that failed before it, run against the unfixed code (pgTAP against the database before `db:reset`, Vitest by reverting the logic for one run, the order check by a mutation inside a rolled-back transaction).

1. **D2 did not cover push devices (fixed).** `register_push_subscription_impl` checked membership with a direct read of `business_members`. An enrolled owner at `aal1`, holding only a stolen email code, could register their own OneSignal device and receive every booking push. They could also unregister the real owner's devices. 0009 now redefines both `_impl`s with the 0007 bodies unchanged except for the access check:
   - `register` requires `private.session_mfa_ok()` and a membership that counts (`private.my_business_ids()`). One device receives the pushes of every business of the user, so it needs the user's strongest level. This also covers a user who is staff in one business and an enrolled owner in another.
   - `unregister` (one id or `p_all`) requires `session_mfa_ok()`. The user's own rows are readable at `aal1`, so removing them one id at a time would do the same as `p_all`.
   - A refusal is `42501` without hint. The device's own OneSignal opt-out never depends on it.

   Tested by pgTAP `14` §9, two checks: the enrolled owner and the staff-here-owner-elsewhere user are refused at `aal1`, and nothing changes; at `aal2` registering and unregistering work; staff still register at `aal1`.
