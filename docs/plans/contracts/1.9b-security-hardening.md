## 0. Decisions (defaults binding for the builders; ⚠ = beyond the literal text of item 10)

**General**
- **G1. New migration `0012_security_hardening.sql`.** 0011 stays as reviewed (its mutation-tested bodies are replaced with `create or replace` in 0012, each «previous body + the stated change», so a review is a diff). 0009–0012 are all unpushed; the remote gets them together in 1.10 (`npm run db:push`).
- **G2.** No new env name, no config change, no new dependency. One new domain error: **AN034 `enrolment_blocked`**.

**(a) Live session in D2**
- **A1. `private.session_mfa_ok()` also requires a live session**: when the JWT carries `session_id`, a row of `auth.sessions` with that id **and** `user_id = auth.uid()` must exist (`private.session_alive()`, §2.3). A revoked owner/manager token stops counting at once in RLS (empty reads) and in every RPC (`42501` without hint). A JWT without `session_id` (pgTAP's synthetic claims; GoTrue always sets it) keeps the 0009 rule. Existence only: neither the row's `aal` nor `not_after` (GoTrue owns expiry; the token's `exp` bounds it).
- **A2. Staff rows are unaffected** in the six membership helpers (the D2 shape `m.role = 'staff' or (select private.session_mfa_ok())` is unchanged). Staff never hold factors; a staff role change or removal already changes the row in the same transaction (D1). Residual: a stolen staff token after «Αποσύνδεση από όλες τις συσκευές» reads until it expires (≤ 1 h) — ADR (ii). **As approved (§7 item 2, alternative, 2026-10-04; §8.6):** staff rows need a live session too: each helper is `(select private.session_alive()) and (m.role = 'staff' or (select private.mfa_level_ok()))`, so a staff token stops at once after «all devices», a role change or a removal; the residual above is closed.
- **A3. Push register/unregister need a live session for every role** (they call `session_mfa_ok()` directly, 0009 review fix 1): a revoked token, staff included, can no longer register a OneSignal device. The app's sign-out already unregisters **before** Auth ends the session (`runSignOut`), so nothing in the app changes.
- **A4. A dead session never opens the code sheet:** `require_fresh_totp()` refuses it first with `42501` **without** hint, and `authorize_factor_change_impl` checks it right after `auth.uid()` (it has no membership check). `has_fresh_totp` (0011) is **not** changed: it still decides `fresh_totp_required` for a live session (aal1 row, unvetted device).
- **A5. Cost:** `session_mfa_ok()` = ≤ 4 index probes (`sessions_pkey`, `factor_enrolment_blocks` PK, `mfa_factors_user_id_idx`, and only for a user without a verified factor the snapshot by `user_id`). In RLS it is an InitPlan inside `(select private.my_business_ids())` etc.: **once per statement**, and never evaluated for a staff-only user (the `or` short-circuits on `m.role = 'staff'`). In `_impl`s once per helper call (2–3 per RPC). Not cached across statements (a revocation inside a transaction must count). **As approved (§8.6):** the session probe moved out of the per-row branch: `(select private.session_alive())` depends on no row, so it is a one-time filter of each helper (exactly one `sessions_pkey` probe per helper and statement, for every role and whatever the plan); the rest of D2 is `private.mfa_level_ok()` (no session probe), and `session_mfa_ok()` = `session_alive()` + `mfa_level_ok()` for its direct callers (push register/unregister).

**(b) Nous copy of every security event**
- **B1. One Nous email per contained event**, a dedicated template per kind (`factor_added_nous`, `factor_removed_nous`), not a copy of each recipient's email. Sent by `dispatch` in the **same notify step** as the other emails: only after `contained` is recorded, once, in parallel with them, idempotency key `security:<event id>:nous`, never retried; a lost lease closes the event `notify_unknown` and nothing is re-sent (1.9 D11). Sent also when the bundle has no other email (sole owner, or no account email).
- **B2. Recipient `SUPPORT_EMAIL`** (server-side, already required by `dispatch`, 1.9 §3.3). Language `el` (`SECURITY_NOUS_LOCALE`), date and time in **UTC** (never a hard-coded `Europe/Athens`, rule 6).
- **B3. Content:** the event kind, the detection instant (UTC), the affected account's email address, the account's owner/manager businesses (name and slug), what was done automatically, how many owner emails went out, the event id (for the read-only SQL of `security-event.md`). Never a secret, a code, a link, an IP, a device name or a factor id.
- **B4. The Nous copy counts** in `emails_sent` / `emails_failed` (no signature change of `record_security_event_result`). The drill and the manual check therefore expect one more email per event.
- **B5.** The business names come from the bundle: `queue_security_notifications` gains two keys, `account_email` and `businesses` (§2.4.5). One assertion of `16_health` (exact bundle keys) is updated accordingly (§6.2).

**(c) Enrolment block after an unauthorized removal**
- **C1. The block is a row of `private.factor_enrolment_blocks`**, written by the detector (0012 replacement, step 6b) when a `factor_removed_unauthorized` event it inserts leaves the user with **no vetted verified factor**: no factor of the run's set C that is not flagged by a `factor_added_unauthorized` event (any run, this one included). So an unauthorized removal plus an unauthorized add in the same 5′ still blocks. Only for an event with non-empty `business_ids` (C5). One audit row `factor_enrolment_blocked` per business (§2.6).
- **C2. ⚠ An unauthorized removal blocks already before the detector sees it** (`private.unauthorized_removal_pending`): the user has no verified factor and a snapshot factor is gone from `auth.mfa_factors` with no remove grant that covers it (the detector's own D8 rule, now one function, `private.remove_grant_for`). Without it, someone who removed the last device with a stolen `aal2` session would, within the same ≤ 5′, take the first-enrolment `add` grant at `aal1` and enrol a device that the detector then counts as approved. Legit removals always write their grant first (app, `mfa-reset`, demotion, `dispatch`), so they never block.
- **C3. What the block does** (`private.enrolment_blocked(uid)` = a block row, or C2): `authorize_factor_change('add')` → **P0001 AN034** (no grant, no audit row; checked before freshness, so never a code sheet); and **⚠ D2: the user's owner/manager memberships do not count at all** (also at `aal2`), so a blocked account reads nothing as owner/manager even with the email code (its staff rows still count). A blocked user's open `add` grants never match (`match_add_grants`), so a device enrolled straight at GoTrue while blocked is flagged by the next run and deleted by `dispatch`; `has_fresh_totp` refuses its codes (it is unvetted).
- **C4. Cleared only by Nous, through `mfa-reset`:** `record_support_action_impl('mfa_reset')` deletes the user's block row in its transaction and returns `enrolment_unblocked`. It **refuses while an unauthorized removal of that user awaits detection** (`55000`, hint `detection_pending`, nothing written): a reset over an undetected removal would be followed by a block at the next run. No separate support action (`SUPPORT_ACTIONS` unchanged). No extra audit row on unblock (the `mfa_reset` rows with ticket and reason are the record).
- **C5.** No block when the account is owner/manager nowhere at detection (`business_ids` empty, like 1.9 D18: nothing to protect, no audit row possible). A block survives demotion and re-promotion; it goes only with `mfa-reset` or the user's deletion (cascade); never purged. **As approved (§7 item 17, alternative, 2026-10-04; §8.6):** `mfa-reset` also lifts the block of a user who is owner/manager nowhere any more (demoted to staff, or removed), so Nous can always lift a block.
- **C6. The PWA:** `decideAuthRoute` gains the route `blocked` (owner/manager, no verified factor, blocked) → `/mfa/blocked`, a plain-language «Επικοινώνησε με τη Nous» screen (the lost-device contact links and «no bypass» line, Nous contact from `VITE_SUPPORT_*`), never the wizard and never the code sheet. The loader asks the server (`factor_enrolment_blocked()`) only when it would otherwise decide `enroll`.
- **C7. Residual (documented, not closed):** a device enrolled less than ~5′ before it is removed is not in the snapshot yet, so for a user whose **only** device it was, nothing blocks until the next run (the transient pass then raises the removal event and blocks). After `mfa-reset` the first sign-in with the email code still enrols: the runbook secures the mailbox first and resets with the user on the phone.

**Estimate:** (a) 0.25 day, (b) 0.25 day, (c) 1 day (SQL, PWA, drill, runbooks) ≈ **1.5 days**.

### 2.4 Replaced functions
